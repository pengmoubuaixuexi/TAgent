# Personal model connections

Apply V064 after the ownership migrations V062/V063. The migration uses the current connection database. It adds encrypted personal credentials and per-user auxiliary service consent; existing platform API rows remain compatible.

Configure `MODEL_SECRET_MASTER_KEY` (or `agent.model-secrets.master-key`) as a deployment secret containing a Base64-encoded 32-byte random key. Keep the same key across application instances and restarts, and back it up separately from database dumps. Losing or replacing it makes existing personal credentials unreadable. An empty key keeps platform models available but disables saving/using personal secrets. This release supports rotating provider credentials in the UI; rotating the encryption master key requires a separate controlled re-encryption procedure.

Set `agent.model-connections.allowed-hosts` to a comma-separated exact hostname list. The application defaults are `api.openai.com,api.deepseek.com,api.siliconflow.cn,api.xiaomimimo.com`; override them through `PERSONAL_MODEL_ALLOWED_HOSTS` or an explicit deployment property. An explicit profile value takes precedence over the application default. Personal connections require HTTPS on port 443, reject URL credentials/query parameters, and check public DNS and the stored origin on each HTTP attempt. Requests do not follow redirects. The operator must trust and control the allowlist: DNS is checked but the resolved IP is not pinned across the later HTTP client's DNS lookup. Private endpoints require a separately designed trusted proxy; do not broadly allow internal hosts.

Open `/models.html` while signed in. Create a connection with the provider's model ID and key, explicitly choose whether the account permits platform auxiliary services, and optionally verify it with a `GET /models` request. Verification generates no model output; providers that do not expose `/models` may reject this check even if chat is supported. Saving itself makes no provider request. Choose the new personal model in My Agents or draft generation. Pages and APIs return metadata and masks, never decrypted credentials.

Rotation encrypts a new key with a new credential version; revocation disables the API and secret. Cached clients resolve the key and authorization on every attempt, so subsequent requests take effect immediately. An HTTP request already dispatched cannot be recalled. Re-enabling a revoked connection requires submitting a new key. Verification status is cleared whenever a key changes.

Personal main-model and draft requests use that user's provider account. Router/summary/planning helpers, embeddings and reranking remain platform services with platform credentials and require the user's auxiliary consent. They never silently borrow another user's key or repurpose a chat key as an embedding key. Users with no policy row retain existing platform behavior; saving a new personal connection defaults to denying auxiliary services unless selected. Server-owned startup catalog indexing uses an explicit, bounded system scope and records `SYSTEM`; user evaluations remain user-scoped. Provider-source request logs contain identifiers and versions only. Persistent usage/pricing records are handled by the usage subsystem.

Offline verification: `PersonalModelConnectionTest` uses an in-memory H2 database, synthetic credentials, stub DNS and a mocked verification client. It checks encryption metadata, owner isolation, transactional rollback, live rotation/revocation, consent and origin checks. H2 does not replace MySQL migration/integration validation. `models-ui.integration.cjs` serves static assets and a loopback mock API, blocks non-loopback browser requests and exercises create, verify, rotate, revoke, consent, CSRF and secret clearing.
